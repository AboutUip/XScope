# 并发与多窗口

[English](concurrency.md)

## 支持的工作方式

用户可以：

- 在**一个进程内跑多个任务**
- 把任务**拖出为独立窗口**
- **多次启动 `exe`**，并行调研

同一项目允许被多个进程/窗口同时打开。

## 决策：窗口 vs 进程

| 操作 | 默认行为 | 原因 |
|------|----------|------|
| 拖出/分离为独立窗口 | **同进程新窗口** | 同步简单、可共享内存中服务，仍有独立工作区感觉 |
| 再开一个 `exe` / 第二实例 | **新进程** | 重任务真隔离；依赖库锁 + IPC |

UI 优先：拖出窗口应轻快；每次拖出都新开进程更重、更不稳。

## 同项目多写者

策略：**任一参与方可写**；写操作在数据库锁上**排队**。

- 优先**短事务**
- 接受多进程写入可能比单进程慢
- 不为高频跨进程写风暴设计；调研负载是突发型，不是交易系统热路径

加密 SQLite（同一时刻单写者）是持久化状态的权威来源。

## UI 联动（必须）

多个窗口/进程打开**同一项目**时，用户可见状态（打开/保存、任务进度、结构变更）必须联动。

做法：

1. **持久状态** → 加密 SQLite（以及项目目录下的文件）
2. **实时通知** → 按 `project_id`（及工作区标识）区分的本地 IPC 事件总线

当该总线跨网络/回环边界，**并且**驱动 UI 渲染/信息交换时，载荷**必须**为 **XAIOP**（流式 Snapshot/Diff）。见 [流式与 XAIOP](streaming-xaiop.zh-CN.md)。

事件用于提示刷新或应用小更新；若冲突或丢消息，以数据库为准重新加载。

IPC 传输在可移植层后按平台选择（桌面可用命名管道/本地套接字等）。具体传输是实现细节；契约是“项目范围的 XAIOP（面向 UI 时）+ 不确定时从存储重载”。

## 实践规则

- 打开项目时在该项目总线上注册进程/窗口
- 关闭时干净注销
- Worker 避免长时间写事务拖慢其他窗口
- `files/` 下写文件尽量使用原子替换等稳妥模式
