# 安全与密钥

[English](security.md)

## 目标（务实）

防御常见风险：

- 库文件被拷走时，不应直接暴露明文调研数据或 API Key
- 本机其他应用不应轻易读到密钥

第一版不做极限加固：例如用户会话内已有完整恶意软件、类反作弊强度等，暂不纳入。

**无登录**。安全方案必须在无账号前提下成立。

## 密钥类型

| 秘密 | 范围 | 存放 |
|------|------|------|
| 大量搜索引擎/扩展 **API Key** | **全局**（所有项目共用） | 加密的全局库（或同一套加密背后的全局秘密存储） |
| 项目调研内容 | 每项目 | 加密项目库 + 项目目录下文件 |

## 加密方案（第一版已实现）

1. **主密钥**（32 字节）存放在 `global.db` 旁，用 **Windows DPAPI** 包装。
2. `global.db` 中的**秘密 / API Key** 在该主密钥下用 **AES-256-GCM** 封装。
3. 库文件只出现在客户端提供的私有 `data_root` 下。
4. 完整 SQLCipher 级页加密可作为后续升级，藏在 `storage::Database` 边界之后。

后续平台端口：macOS Keychain、Android Keystore 等。

可接受的代价（本地、无登录产品常态）：重装系统配置、换机、或清除密钥材料后，可能需要重新填写 API Key；除非后续增加备份/导出能力。

## API Key

- **全局**存放，不按项目隔离
- 一律通过 SDK 秘密 API 读写 — 不以明文记日志
- 预期会有**很多** Key；schema/API 应按 provider → secret 的列表/映射设计，而不是写死单个字段

## 客户端 vs SDK

- 客户端：选择私有 `data_root`，默认不在 UI 日志打印秘密
- SDK：静态加密、参数化 SQL、尽量减少密钥字节在 API 中的暴露面

## 最小第一版

先交付加密 + 密钥保护管线与极小 schema。不在功能出现前写完整威胁模型长文；随“持有秘密”的功能扩展再加强控制。
